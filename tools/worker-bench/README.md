# Worker benchmark

`Run.ps1 -Models <read-only model folder> -Resolver <existing Rhino.Inside resolver> -Output <new folder>` builds Release and records the small single-view startup control and eight-view M/L in-process/1/2/4-worker matrix, fresh-process cold then retained-scene warm. The exporter terminates before the coordinator starts workers: at most four owned RhinoCore processes, including the in-process baseline host. No process enumeration, attachment or unrelated termination is used.

The benchmark uses the production native/composed/section compute code, native threading off, hidden lines on, document tolerance and a 12 GiB baseline scheduler budget (to permit a comparison outside the product host's 512 MiB admission). Workers get 6 GiB OS job caps for the measurements. Production defaults remain 4 GiB per worker. The generated model's named long section and a z=1.2 plan are included with North/South/East/West/Top/SW. Scene encoding/capture are separate observations. Cold wall includes process startup, handshake, scene shipping/preparation, all view solves and compressed serialized reply transfer; warm wall retains scenes and workers. Hash verification occurs outside the recorded worker batch wall.

Every full result is SHA-256 compared byte for byte after excluding timings and diagnostic prose only. Geometry archives, source metadata, classification, depth geometry, section provenance, hatches, settings and quality are included; nothing is rounded or resorted by the comparator. Missing/mismatched views are recorded per view. `baseline.json`, `workers-{1,2,4}.json`, scene/request archives and expected result hashes form the evidence. Stable baseline result payloads are also retained to diagnose mismatches. Keep the complete folder outside Git; hash it in a manifest before sharing measurement claims.

Baseline memory is sampled process-private bytes every 25 ms. Worker memory is the sum of OS Job Object peak commit counters, a conservative upper bound rather than aligned aggregate peak. External application/agent contention and OS caches are uncontrolled; report these runs as n=1 and do not infer a universal performance model.


Review/default path: export M with the ordinary `export` mode; export only owned L scene/requests with `scene` (no baseline compute). Then run `pool <folder> <worker directory> <passes>`. This uses the production pool's memory sizing, retention, retry and handshake path with no count/cap environment variables. Its coordinator never initializes RhinoCore. `pool-defaults.json` records RAM, chosen count/cap/budget, per-view hashes and errors, and job peaks. M folders have in-process hashes for strict comparison; scene-only L runs establish default admission/success without claiming an unmeasured new L reference. The original `workers` mode remains an explicit fixed-count/cap experiment.
